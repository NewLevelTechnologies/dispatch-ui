# Dispatch Mobile

React Native app built with Expo (SDK 57) and Expo Router, sharing `@dispatch/api`,
`@dispatch/utils` and `@dispatch/i18n` with the web app.

## Local development

```bash
corepack enable          # once — pnpm comes from package.json's packageManager
pnpm install             # from the repo root
cp apps/mobile/.env.example apps/mobile/.env

cd apps/mobile
pnpm dev                 # Metro; press i for the simulator
```

`EXPO_PUBLIC_*` values are **inlined into the bundle at build time**, so after editing
`.env` restart with `pnpm dev --clear`. A plain restart keeps serving the old values.

Tests use Jest (not vitest — see `jest.config.mjs` for why):

```bash
pnpm test
pnpm test:coverage
```

## Releasing to TestFlight

Builds go through [EAS](https://docs.expo.dev/build/introduction/). `eas-cli` is
deliberately **not** a dependency of this workspace: it pulls native install scripts
(`dtrace-provider`, `protobufjs`) that have nothing to do with the app, and pnpm 10+
would need each allowlisted in `pnpm-workspace.yaml`. Run it through `pnpm dlx`
instead.

### One-time setup

```bash
cd apps/mobile

pnpm dlx eas-cli login          # Expo account
pnpm dlx eas-cli init           # links the project, writes extra.eas.projectId to app.json
```

`eas init` is the step that adds `extra.eas.projectId` to `app.json` — commit that
change, since every later build resolves the project from it.

### Build and submit

```bash
pnpm build:ios                  # eas build --platform ios --profile production
pnpm submit:ios                 # eas submit --platform ios --profile production
```

The first build asks how to handle signing. Letting EAS generate and store the
distribution certificate and provisioning profile is the low-friction answer; it
needs your Apple Developer credentials once and reuses them after.

`eas submit` needs the App Store Connect app to already exist — it does — and will ask
for an App Store Connect API key or your Apple ID. An API key is the better choice for
anything that later runs unattended.

### Things that will trip you up

**The App Store Connect record must use `net.newleveltech.dispatch`.** That is the
`ios.bundleIdentifier` in `app.json` and the `submit.production.ios.bundleIdentifier`
in `eas.json`. A mismatch fails at submit time, after the build has already run.

**`.env` never reaches the build server.** It is gitignored, and EAS uploads the
project respecting `.gitignore`, so the build would start with no `EXPO_PUBLIC_*` at
all and `src/config/amplify.ts` would throw on launch. That is why every profile in
`eas.json` carries its own `env` block. Change a value in `.env` and you must change
it in `eas.json` too — they are not linked.

**These builds point at dev.** Every profile currently uses the dev API and the dev
Cognito pool, so TestFlight testers sign in with dev users and see dev data. That is a
deliberate choice for proving the pipeline. Before real testers, give the `production`
profile its own values — or move them to EAS secrets if they ever stop being public.

**Build numbers must increase.** The `production` profile sets `autoIncrement`, and
`cli.appVersionSource` is `remote`, so EAS owns the build number rather than
`app.json`. Do not also bump it by hand — that is how you get a collision.

**`version` in `app.json` is the user-facing version.** Bump it for a new TestFlight
round; `autoIncrement` only moves the build number underneath it.

## Native builds

`ios/` and `android/` are generated by `expo prebuild` and gitignored — this app uses
Continuous Native Generation, so `app.json` and its plugins are the source of truth.
Regenerate with `pnpm exec expo prebuild --platform ios --clean` after changing native
config; never hand-edit inside `ios/`.

To run a native build on the simulator without EAS:

```bash
pnpm ios                        # expo run:ios
```
